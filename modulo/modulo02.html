Arquiteturas de Sistemas Distribuídos, Threads e RPC

Este módulo aborda a base arquitetural dos sistemas distribuídos: a criação e o uso de threads, a organização em cliente-servidor e peer-to-peer, a camada de middleware, a comunicação por sockets e o funcionamento do RPC. Também exploramos a definição de interfaces, o empacotamento de dados, a semântica de execução e a importância da idempotência em chamadas remotas.

Objetivos de aprendizagem

  • Compreender o conceito de thread.
  • Diferenciar threads de usuário e threads de kernel.
  • Reconhecer arquiteturas Cliente-Servidor e Peer-to-Peer.
  • Entender a função do middleware.
  • Compreender sockets como mecanismo de comunicação.
  • Explicar o funcionamento básico do RPC.
  • Identificar as funções dos Stubs e Skeletons.
  • Entender marshalling e unmarshalling.
  • Conhecer a finalidade da IDL.
  • Diferenciar semânticas de execução RPC e a relação com idempotência.

1. Threads

Uma thread é a unidade básica de utilização da CPU dentro de um processo.

Uma thread é uma unidade básica de uso da CPU, composta por contador de programa, conjunto de registradores e espaço de pilha. Ela executa dentro de um processo e compartilha código, dados, heap e recursos do sistema operacional com outras threads do mesmo processo.

Os elementos que cada thread possui de forma própria são: contador de programa, registradores e stack/pilha própria.

Código Compartilhado
Dados Compartilhado
Heap Compartilhado
Stack Próprio de cada thread

Exemplo didático

Um servidor web pode criar uma nova thread para atender cada requisição recebida. Assim, várias solicitações podem ser processadas simultaneamente sem que cada uma precise ser um processo separado.

2. Threads de usuário e threads de kernel

Diferentes níveis de suporte para a execução concorrente.

Threads de usuário

São threads gerenciadas pelo espaço do usuário, sem depender diretamente do núcleo do sistema operacional.

São mais leves, mas dependem da implementação da biblioteca ou da aplicação.

Threads de kernel

São threads conhecidas e gerenciadas pelo kernel do sistema operacional.

Permitem maior integração com o escalonamento do sistema operacional.

3. Arquiteturas de sistemas distribuídos

Organização dos papéis e da interação entre componentes.

Cliente-Servidor

Divide claramente os papéis entre cliente e servidor. O cliente faz requisições e o servidor fornece serviços.

Estrutura comum em aplicações distribuídas e sistemas web.

Peer-to-Peer

Componentes colaboram diretamente entre si, sem a necessidade de um papel único de servidor central.

Cada nó pode receber e fornecer serviços.

4. Middleware

Uma camada de abstração sobre rede e sistema operacional.

O middleware fornece uma camada de abstração entre a aplicação e os mecanismos de rede e sistema operacional. Isso facilita o desenvolvimento, ocultando detalhes de comunicação e de infraestrutura.

5. Sockets

Abstração para comunicação via rede TCP/UDP.

Os sockets são usados para permitir comunicação por rede, sendo uma abstração para comunicação TCP/UDP. Eles permitem a troca de dados entre processos em diferentes máquinas ou mesmo no mesmo sistema.

6. RPC — Remote Procedure Call

Chamada de procedimento remoto como se fosse local.

O mecanismo de RPC permite que um programa chame um procedimento ou função executado em outro espaço de endereçamento, geralmente em outro computador da rede, sem precisar programar explicitamente todos os detalhes da comunicação.

O objetivo é fazer com que a chamada remota pareça uma chamada local para o programador. Por exemplo, calcularSaldo(contaId) pode executar em um servidor remoto.

7. Client Stub, Server Stub / Skeleton e RPC

Componentes essenciais para esconder a comunicação de rede.

Client Stub

Representa o procedimento remoto no cliente. Recebe a chamada, realiza o marshalling dos parâmetros, envia os dados pela rede e recebe a resposta.

Server Stub / Skeleton

Recebe a requisição remota, executa o unmarshalling dos dados e entrega a chamada ao procedimento correto no servidor.

8. Marshalling e unmarshalling

Empacotamento e desempacotamento dos dados para a transmissão.

O Marshalling é o processo de empacotar e converter parâmetros e argumentos em um formato adequado para transmissão. O Unmarshalling faz a operação inversa, transformando os dados recebidos em uma representação utilizável.

Representações comuns incluem XDR e JSON.

9. IDL — Interface Definition Language

Contrato entre cliente e servidor.

A IDL é usada para definir interfaces remotas de forma independente da linguagem de programação. Ela pode definir funções, parâmetros e tipos de dados e funciona como um contrato entre cliente e servidor.

Exemplos mencionados incluem arquivos .idl e gRPC .proto. A IDL permite gerar componentes necessários para cliente e servidor mesmo quando usam linguagens diferentes.

10. Semântica de execução em RPC

Como a rede e as retransmissões afetam a execução.

At-least-once

Uma operação pode ser executada mais de uma vez, porque a chamada pode ser retransmitida ou duplicada antes da confirmação.

Pode resultar em múltiplas execuções.

At-most-once

Procura garantir que o procedimento remoto seja executado no máximo uma vez, mesmo diante de falhas ou retransmissões.

É a semântica importante para evitar duplicidade.

Exactly-once

O ideal seria executar exatamente uma vez, mas depende da implementação e das condições de falha.

É um objetivo desejado, porém mais difícil de garantir.

11. Idempotência

Executar a operação uma ou várias vezes produz o mesmo resultado final.

Uma operação é idempotente quando executá-la uma ou várias vezes produz o mesmo resultado final. Esse conceito é muito importante em sistemas distribuídos, especialmente quando há retransmissões de mensagens.

  • Idempotente: "definir saldo para R$100".
  • Não idempotente: "subtrair R$100 do saldo".

Em operações financeiras, a idempotência é crucial para evitar efeitos colaterais indevidos em caso de retransmissão.
